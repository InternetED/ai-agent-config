# Triage

Move issues—and configured external pull requests—through a small, maintainer-directed state machine.

## Use when / Not for

- **Use when:** reviewing what needs maintainer attention, investigating a specific issue or PR, assigning a triage state, or drafting an agent-ready brief.
- **Not for:** tickets from `to-tickets` that are already agent-ready, or implementing a ready issue—use `implement`.

Every comment or issue posted to the issue tracker during triage **must** start with:

```markdown
> *This was generated by AI during triage.*
```

## Roles

Assign exactly one category and one state:

- **Category:** `bug` for broken behavior; `enhancement` for a feature or improvement.
- **State:** `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`.

If state roles conflict, stop and ask the maintainer. Tracker label strings may differ from these canonical names; use the mapping from `setup-matt-pocock-skills`.

Read [AGENT-BRIEF.md](AGENT-BRIEF.md) when preparing a durable agent brief.

Read [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) when rejecting an enhancement or consulting `.out-of-scope/`.

Read [reference.md](reference.md) only for state transitions, the needs-info template, PR deltas, label mapping, or resuming prior triage notes.

## Invocation

Interpret natural-language requests such as “Show me anything that needs my attention,” “Let's look at #42,” “Move #42 to ready-for-agent,” or “What's ready for agents?” Resolve a bare identifier according to tracker configuration.

## Show what needs attention

1. Query three buckets, oldest first: unlabeled; `needs-triage`; and `needs-info` with reporter activity after the last triage notes.
2. Include configured external PRs, excluding collaborators' in-flight PRs only during discovery; mark every row `[PR]` or `[issue]`.
3. Show counts and a one-line summary for each item, then let the maintainer choose.

## Triage a specific issue or PR

1. **Gather context.** Read the complete thread, labels, authorship, dates, prior triage notes, and PR diff when applicable. Use the domain glossary and relevant ADRs. Search by domain concept for an existing implementation and inspect `.out-of-scope/*.md` for prior rejection.
2. **Recommend.** Present category and state with reasoning and a relevant codebase summary, including the redundancy and prior-rejection checks. Wait for maintainer direction.
3. **Verify.** Reproduce a bug from the report, or check out a PR and run relevant commands. Report confirmed with code path, failed, or insufficient detail.
4. **Grill if needed.** Call the Skill tool for both `grilling` and `domain-modeling`; ask one round at a time and update `CONTEXT.md` or ADRs as decisions land.
5. **Apply the outcome.** Post the required brief or notes, set exactly one category and state, and close `wontfix` items with the appropriate explanation or out-of-scope record.

## Quick state override

Trust an explicit maintainer override. Confirm the exact role changes, comment, and closure before acting, then skip grilling. When moving directly to `ready-for-agent`, ask whether they want an agent brief.

## Verification

Before finishing:

- Every posted item or comment begins with the AI disclaimer.
- The item has exactly one category and one state role using configured labels.
- The recommendation includes redundancy, prior-rejection, and claim-verification results.
- Prior triage answers were preserved and not re-asked.
- The applied outcome includes its required brief, notes, closure explanation, or out-of-scope record.
